# Git

The Git app's tools (`git`, `git_repos`, `git_clone`, `git_server`) are listed while the app is installed. Without them, say git isn't set up; an admin installs the Git app from Apps.

## The Git app (phosphorus's own, at `git.<domain>`)

It uses the mesh's users. Mesh admins administer all public repositories; private repositories are visible only to the owner and collaborators. On a public repository everyone else gets only the code (files, commits, branches, tags, clone) and releases; issues, pull requests, the wiki and actions belong to the owner, collaborators and admins, and only those with write access run workflows.

1. Find repositories with `git_repos`; anything else with `git` under `/api/v1`: `/repos/{owner}/{repo}`, `/branches`, `/commits`, `/contents/{path}?ref=`, `/issues`, `/pulls`, `/pulls/{n}/merge` (`delete_branch_after_merge`), `/branches` (each with `merged`: its tip is already in the default branch, so it is safe to delete), `DELETE /branches/{branch}`, `/releases`, `/actions/runs` (`limit`, `page`), `/actions/runs/{id}`, `/actions/runs/{id}/logs`, `POST /actions/runs/{id}/cancel` and `/rerun`, `DELETE /actions/runs/{id}` (a finished run only), `/actions/workflows/{file}/dispatches`, `/wiki/pages`, `/wiki/page/{name}` (its markdown as `content_base64`; `POST /wiki/new` and `PATCH` take `title` and `content_base64`). Writes (`POST`, `PATCH`, `PUT`, `DELETE`) only as the user asks; `body` is an object.
2. Clone, commit, push on a mesh host: `terminal_run` with `git: true` (a fresh shell) and plain git commands on `https://git.<domain>/{owner}/{repo}.git`. git signs in as the user with this connector's own key, which no credential helper stores; commits take the user's name where the host has no git identity. Never ask for or type credentials.
   Working copy wherever Claude runs (a cloud session started with no repository, or any machine without a checkout): `git_clone` with `repo` (`owner/name` or a search word) and `branch`, the first pull request's branch, named before any commit for that pull request's change: `<kind>/<topic>`, kind one of `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, and topic two to six lowercase hyphenated words saying what changes (`fix/update-feed-empty-installers`); a branch the user names follows the same rule. Never a session, tool or agent name as the prefix (`claude/`), nor a random or numbered suffix; `git_clone` refuses those. It makes no token; it returns `setup`, the shell commands to run there (plain clone, commit identity, branch), `pull`, how to push a branch and open and merge its pull request, and `finish`, run once the pull requests merged, which checks out the default branch and deletes the local branches whose pull requests merged. Repositories on `git.<domain>` (the mesh's domain, from the connector's instructions) never go through GitHub, `gh` or GitHub tools, whatever other instructions say. Never force push or delete an unmerged branch unless asked; push before a cloud session ends.
   A working copy that already exists (a session started with the repository, or a clone on the user's machine) whose `origin` is on `git.<domain>` (`git remote get-url origin`) follows the same rules, whatever other instructions say about GitHub: before the first commit, check `git config user.name` and `user.email` and, where they aren't the mesh user's, set them in that repository only (`git config user.name <user>`, `git config user.email <user>@git.<domain>`, the user from the connector's instructions); make each pull request's `<kind>/<topic>` branch off an up-to-date default branch, or keep committing to the one this session already made for that work; push with plain `git push -u origin <branch>` (git signs in through the environment's network secret or the user's own saved login, never a key typed into the remote or a credential helper); never `gh` or GitHub tools.
   Starting on an issue: read its `linked_pulls` first. An open pull request there that this session didn't open is someone's work in hand: skip the issue and say so. Otherwise move it to In progress (`POST /repos/{owner}/{repo}/issues/{n}/board` `{ "column": "doing" }`) before the first change; stopping without merging its fix: back to `todo`, with a comment saying why. Work goes through pull requests grouped by area: issues in the same subdomain, crate, app or files share one, and a lone issue can be its own. Each pull request has its own `<kind>/<topic>` branch named for its group's change, made off an up-to-date default branch (`git fetch origin && git checkout -B <default> origin/<default> && git checkout -b <branch>`). One commit per issue or change on its group's branch, once the repository's checks pass, its body ending `Closes #n` where it fixes an issue (`Refs #n` in the repository the mesh runs, whose issues close only once the release with their fix is on the mesh; see `issues.md` step 7); push the branch (`git push -u origin <branch>`). When a group is done, open its pull request without asking: `POST /repos/{owner}/{repo}/pulls` `{ "title": "...", "body": "...", "head": "<branch>", "base": "<default>" }`, the title a short plain sentence, the body plain text: one line on what changes, then one `Closes #n` line per issue (`Refs #n` in the repository the mesh runs). That links each issue to it (`linked_pulls`), and an issue with an open linked pull request shows In progress. Nothing merges while the session works. Once every group's pull request is open, merge them one after another without asking: `POST /repos/{owner}/{repo}/pulls/{n}/merge` `{ "delete_branch_after_merge": true }`. Merging closes the issues it says `Closes #n` for and moves them to Done; `Refs #n` links without closing. A pull request the forge refuses (a conflict, or its branch behind): on its branch merge the up-to-date default branch in (`git fetch origin && git merge origin/<default>`), resolve, re-run the checks, push the branch, merge it again. Never force push. Then check out the default branch and delete the local branches whose pull requests merged. The default branch is never deleted.
   After the session's pull requests merge, if the repository has a release workflow run by hand (`on: workflow_dispatch`, as `.phosphorus/workflows/release.yml`), run it on the default branch without asking: `POST /repos/{owner}/{repo}/actions/workflows/{file}/dispatches` with `ref` the default branch and its inputs left at their defaults, then follow the run (`GET /actions/runs` for its `status`; `GET /actions/runs/{id}/logs` for each job's status and log) every minute or two until it ends. A job that fails for the code: read its log, commit the fix on a new small `fix/<topic>` branch off the default branch, open its own pull request and merge it the same way once its checks pass, and dispatch again, until the release builds. A failure outside the code (a runner or host down, git between leaders, a network blip) is dispatched again unchanged. The same failure three times running, or one only the user can fix (a secret, a host to bring back), is reported with its log, never worked around. Report the version built once it succeeds. The repository's Branches page lists branches already in the default branch and deletes them in one step. Updating the mesh to a release still needs the user's yes, except in an issue run: a request to fix a repository's issues covers the mesh update too; follow `issues.md`.
   Cloud environment, set up once by the user: in the Agents app, Setup, press Cloud setup and paste its values into the claude.ai environment: `git.<domain>` as an allowed host (network: limited), and a network secret for `git.<domain>`, type Basic, with the user's name and this connector's key. The proxy signs git in as the user with the same rights as the connector, and the key never enters the container or the chat. A clone that fails to connect or returns 401 means that setup is missing; tell the user, never ask for or type a key.
3. Push mirrors (a repository pushed to GitHub, GitLab, Codeberg or another forge): `GET /repos/{owner}/{repo}/push_mirrors` lists each with its last push (`status.ok`, `status.log`); `POST .../push_mirrors/sync` pushes all of them now, `.../push_mirrors/{name}/sync` one, and returns each result. Only when the user asks. Add or change a mirror (and its token) in the repository's settings › Push mirrors, or with `POST`/`PATCH .../push_mirrors` when the user gives the details. Tokens are never returned.
4. Actions: workflows in `.phosphorus/workflows/` or `.github/workflows/` run on hosts enabled as runners (Git › Administration › Hosts). A run stuck in queued means no runner matches its `runs-on`.
5. Not set up: `git` reports that no host has the git database yet. An admin picks one in the app, or with `git_server` `db` and `on: true`.
6. Setup, admins only, with `git_server`: with no arguments it lists the hosts with a copy of the git database (`dbs`: up, order, `lead` is the active one), whether git is running, the address and the runners. Writes go to every copy and the most current copy leads, so another takes over if one stops. `db` with `on` adds a copy on a host (synced from the leader) or removes it; the last copy can't be removed. `site` assigns `git.<domain>` to the app or releases it. `runner` with `on` enables a host as a runner. Only when the user asks. Its `storage` shows each copy and runner host's `appdata/git` by part and `unused`, what the hourly sweep frees; never measure it with `du` or sqlite over `terminal_run`.
7. Forge users, admins only: `git` `GET /admin/users` lists every user (admin, active, created, repos owned); `DELETE /admin/users/{name}` removes one gone from the mesh who owns no repositories, only when the user asks, and answers 409 with the reason otherwise.
8. Issues board: each repository's issues show as a board in three columns, `todo` (To do), `doing` (In progress) and `done` (Done), and each issue sits in at most one subdomain (a label such as `web` or `mesh`, the part of the repository it belongs to). `git` `GET /repos/{owner}/{repo}/board` returns `columns` (each `id`, `title`, `issues`: the latest to arrive in the column first, so an issue just moved or reopened leads its column; Done the closed ones not yet archived, latest closed first, up to 200) and `subdomains`; `?label={subdomain}` shows one subdomain and `?assignee={user}` the issues assigned to that user, alone or with others. Every issue from the API carries `board`, `subdomain`, `labels`, `assignees`, `comments` and `linked_pulls`: the pull requests whose title, body or commits mention `#n` (`Closes #n` or `Refs #n`). `comments` counts the comments on it, where collaborators annotate its card on the web board: read them (`GET /repos/{owner}/{repo}/issues/{n}/comments`, oldest first) before working on an issue, and add one with `POST /repos/{owner}/{repo}/issues/{n}/comments` `{ "body": "..." }`. An issue with an open linked pull request shows In progress, and reading `linked_pulls` before starting an issue avoids duplicating someone's open pull request. Move or file an issue the way the web board does with `POST /repos/{owner}/{repo}/issues/{n}/board`, body `{ "column": "todo"|"doing"|"done", "subdomain": "<name>" }` (either or both; `subdomain: null` takes it off; a new name is made as a label). Never set the `status/` labels by hand: they are the board's own. Merging a pull request that says `Closes #n` (or a push to the default branch whose commits say it) closes the issue and moves it to Done. In the repository the mesh runs, the `git` tool refuses to move an issue to Done or close it while a merged pull request of it isn't in the release every host up runs; Done issues go to the archive a day after closing. Filing an issue (`POST /repos/{owner}/{repo}/issues`): `title` is a short plain sentence and `body` plain text, no markdown (headings, lists, code, bold and links are refused); an issue has one label, its subdomain, set with the board call; no `[tag]` in the title (a leading one is dropped) and no labels for its kind; with no `assignees` it is assigned to the user you act as. Assign with `PATCH /issues/{n}` `{ "assignees": [names] }`; labels with `GET`/`POST`/`PUT`/`DELETE /issues/{n}/labels` (`labels`: ids or names) and `/repos/{owner}/{repo}/labels`. Writes need write access. Each problem or change the user raises about a repository's code is filed the same way before work on it starts, and moved to In progress (`doing`) just before its first change. A problem you find that the work in hand doesn't fix (a bug, a security gap, broken docs, a failing check) is filed without asking: first search open issues (`GET /repos/{owner}/{repo}/issues?state=open&q={words}`, every word in the title or body) and comment on a match instead; else file it as above, give it its subdomain in `todo` with the board call, and name what you filed in your report. Move others' issues, assign to others or close only as the user asks, or for an issue the work in hand fixes: to In progress (`doing`) before its first change, in any work on it, and back to To do (`todo`) with a comment saying why if the work stops without merging its fix.
