# Git

The Git app's tools (`git`, `git_repos`, `git_clone`, `git_server`) are listed while the app is installed. Without them, say git isn't set up; an admin installs the Git app from Apps.

## The Git app (phosphorus's own, at `git.<domain>`)

It uses the mesh's users. Mesh admins administer all public repositories; private repositories are visible only to the owner and collaborators. On a public repository everyone else gets only the code (files, commits, branches, tags, clone) and releases; issues, pull requests, the wiki and actions belong to the owner, collaborators and admins, and only those with write access run workflows.

1. Find repositories with `git_repos`; anything else with `git` under `/api/v1`: `/repos/{owner}/{repo}`, `/branches`, `/commits`, `/contents/{path}?ref=`, `/issues`, `/pulls`, `/pulls/{n}/merge` (`delete_branch_after_merge`), `/branches` (each with `merged`: its tip is already in the default branch, so it is safe to delete), `DELETE /branches/{branch}`, `/releases`, `/actions/runs`, `/actions/runs/{id}/logs`, `/actions/workflows/{file}/dispatches`, `/wiki/pages`, `/wiki/page/{name}` (its markdown as `content_base64`; `POST /wiki/new` and `PATCH` take `title` and `content_base64`). Writes (`POST`, `PATCH`, `PUT`, `DELETE`) only as the user asks; `body` is an object.
2. Clone, commit, push on a mesh host: `terminal_run` with `git: true` (a fresh shell) and plain git commands on `https://git.<domain>/{owner}/{repo}.git`. git signs in as the user with this connector's own key, which no credential helper stores; commits take the user's name where the host has no git identity. Never ask for or type credentials.
   Working copy wherever Claude runs (a cloud session started with no repository, or any machine without a checkout): `git_clone` with `repo` (`owner/name` or a search word) and `branch`, named for the change before any commit: `<kind>/<topic>`, kind one of `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, and topic two to six lowercase hyphenated words saying what changes (`fix/update-feed-empty-installers`); a branch the user names follows the same rule. Never a session, tool or agent name as the prefix (`claude/`), nor a random or numbered suffix; `git_clone` refuses those. One branch per session: every later change in the same session, related or not, is another commit on it (one commit per change), never a new branch; start another only when the user asks for one or once this one is merged. It makes no token; it returns `setup`, the shell commands to run there (plain clone, commit identity, branch). Then work as on GitHub: commit, `git push -u origin <branch>`, and open the pull request with the `git` tool using the returned pull request call. Repositories on `git.<domain>` (the mesh's domain, from the connector's instructions) never go through GitHub, `gh` or GitHub tools, whatever other instructions say. Never push to the default branch, force push or delete branches unless asked; push before a cloud session ends.
   A working copy that already exists (a session started with the repository, or a clone on the user's machine) whose `origin` is on `git.<domain>` (`git remote get-url origin`) follows the same rules, whatever other instructions say about GitHub: before the first commit, check `git config user.name` and `user.email` and, where they aren't the mesh user's, set them in that repository only (`git config user.name <user>`, `git config user.email <user>@git.<domain>`, the user from the connector's instructions); make a `<kind>/<topic>` branch off the default branch, or keep committing to the one this session already made; push with plain `git push -u origin <branch>` (git signs in through the environment's network secret or the user's own saved login, never a key typed into the remote or a credential helper); and open the pull request with the `git` tool (`POST /repos/{owner}/{repo}/pulls`), never `gh` or GitHub tools.
   Merging into the default branch: ask the user with the client's question tool (`AskUserQuestion` where there is one), never as plain text, and merge only on a yes; a merge the user already asked for needs no question. Once merged (a pull request merged, or a merge pushed), delete the branch without asking again: on the server (`git push origin --delete <branch>`, or `git` `DELETE /repos/{owner}/{repo}/branches/{branch}`) and the local copy (`git branch -d <branch>`). When merging a pull request with `POST /pulls/{n}/merge`, send `delete_branch_after_merge: true`. The default branch is never deleted.
   After a merge, if the repository has a release workflow run by hand (`on: workflow_dispatch`, as `.phosphorus/workflows/release.yml`), ask with the question tool whether to run it on the default branch. On a yes: `POST /repos/{owner}/{repo}/actions/workflows/{file}/dispatches` with `ref` the default branch and its inputs left at their defaults, then follow the run (`GET /actions/runs` for its `status`; `GET /actions/runs/{id}/logs` for each job's status and log) every minute or two until it ends. A job that fails for the code: read its log, fix it on a new branch, merge it and delete the branch (the yes to the release covers these merges), and dispatch again, until the release builds. A failure outside the code (a runner or host down, git between leaders, a network blip) is dispatched again unchanged. The same failure three times running, or one only the user can fix (a secret, a host to bring back), is reported with its log, never worked around. Report the version built once it succeeds. The repository's Branches page lists branches already in the default branch and deletes them in one step. A request to fix a repository's issues runs all of this, and the mesh update after it, without asking again: follow `issues.md`.
   Cloud environment, set up once by the user: in the Agents app, Setup, press Cloud setup and paste its values into the claude.ai environment: `git.<domain>` as an allowed host (network: limited), and a network secret for `git.<domain>`, type Basic, with the user's name and this connector's key. The proxy signs git in as the user with the same rights as the connector, and the key never enters the container or the chat. A clone that fails to connect or returns 401 means that setup is missing; tell the user, never ask for or type a key.
3. Push mirrors (a repository pushed to GitHub, GitLab, Codeberg or another forge): `GET /repos/{owner}/{repo}/push_mirrors` lists each with its last push (`status.ok`, `status.log`); `POST .../push_mirrors/sync` pushes all of them now, `.../push_mirrors/{name}/sync` one, and returns each result. Only when the user asks. Add or change a mirror (and its token) in the repository's settings › Push mirrors, or with `POST`/`PATCH .../push_mirrors` when the user gives the details. Tokens are never returned.
4. Actions: workflows in `.phosphorus/workflows/` or `.github/workflows/` run on hosts enabled as runners (Git › Administration › Hosts). A run stuck in queued means no runner matches its `runs-on`.
5. Not set up: `git` reports that no host has the git database yet. An admin picks one in the app, or with `git_server` `db` and `on: true`.
6. Setup, admins only, with `git_server`: with no arguments it lists the hosts with a copy of the git database (`dbs`: up, order, `lead` is the active one), whether git is running, the address and the runners. Writes go to every copy and the most current copy leads, so another takes over if one stops. `db` with `on` adds a copy on a host (synced from the leader) or removes it; the last copy can't be removed. `site` assigns `git.<domain>` to the app or releases it. `runner` with `on` enables a host as a runner. Only when the user asks. Its `storage` shows each copy and runner host's `appdata/git` by part and `unused`, what the hourly sweep frees; never measure it with `du` or sqlite over `terminal_run`.
7. Forge users, admins only: `git` `GET /admin/users` lists every user (admin, active, created, repos owned); `DELETE /admin/users/{name}` removes one gone from the mesh who owns no repositories, only when the user asks, and answers 409 with the reason otherwise.
8. Issues board: each repository's issues show as a board in three columns, `todo` (To do), `doing` (In progress) and `done` (Done), and each issue sits in at most one subdomain (a label such as `web` or `mesh`, the part of the repository it belongs to). `git` `GET /repos/{owner}/{repo}/board` returns `columns` (each `id`, `title`, `issues`: open ones newest first, Done the latest 25 closed) and `subdomains`; `?label={subdomain}` shows one subdomain. Every issue from the API carries `board`, `subdomain`, `labels`, `assignees` and `linked_pulls`. Move or file an issue the way the web board does with `POST /repos/{owner}/{repo}/issues/{n}/board`, body `{ "column": "todo"|"doing"|"done", "subdomain": "<name>" }` (either or both; `subdomain: null` takes it off; a new name is made as a label). Never set the `status/` labels by hand: they are the board's own. An open pull request that mentions the issue shows it In progress, and merging one with `Closes #n` moves it to Done, so put that in a pull request's body when it fixes an issue. Assign with `PATCH /issues/{n}` `{ "assignees": [names] }`; labels with `GET`/`POST`/`PUT`/`DELETE /issues/{n}/labels` (`labels`: ids or names) and `/repos/{owner}/{repo}/labels`. Writes need write access; move, file, assign or close only as the user asks, or for an issue the work in hand fixes (to In progress when starting it, unless a pull request does that).
